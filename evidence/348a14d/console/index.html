§1live

Live chain state

Read the mandate's current state straight from an RPC of your choice. Nothing is requested until you press the button. The RPC must first report the network's chain id and genesis hash; on a wrong chain, an error or a timeout nothing is shown as verified. The RPC you choose is trusted for every answer it returns.

§2owner

Owner controls

Revoke, recover and withdraw are enabled only when all three hold: the connected signer is the contract's owner_id, the RPC's chain is the chosen network (genesis check), and the mandate account runs the expected code. Each action is shown exactly before anything is signed, and is signed outside this page.

A · Connect a signer

NEAR Connect 0.11.4 External wallets connect through NEAR Connect, from the wallet list in this page (no remote list, no saved or manually added wallets). On mainnet each wallet's adapter is pinned to a commit, checked against its sha256 before it runs, and runs in a sandboxed frame. A browser-extension wallet that announces itself to the page may also appear; it is labelled as not pinned. The wallet signs and broadcasts; the page holds no key and checks every returned transaction on chain against the exact preview. A wallet that ends a request without a hash leaves the action pending until you paste the hash or forget it. Compatibility with a specific wallet is established only when its owner connects it (see About).

Not connected.

B · Runner intent (optional)

Paste the runner's persisted bounded-mandate/external-intent@1 record. Then only that action can be signed, and only if the console's own preview, built from live state, equals it field by field.

C · Owner actions, in journey order

Revoke first (step 5); recovery needs a revoked grant (step 7); withdrawal is the owner's own later step from its Intents account (step 8). Each opens an exact preview; nothing is signed until you confirm it there.

Controls need JavaScript and live state.

Actions in this browser

Pending actions are kept in this browser's storage, keyed by the intent's sha256. After a reload the console only resumes polling; it never signs or sends anything again by itself.

§4about

About this console

  • No backend, no keys. This page is one static file. It holds no private key and no model credential; it reads public RPC state and hands transactions to a signer outside the page.
  • Two sources, never mixed. “Live” values come from the RPC you chose, after its genesis check, at one final block. “Recorded” values come from a sandbox run's evidence file. Neither is ever substituted for the other.
  • Signing adapters. External wallets connect through NEAR Connect (pinned library, in-page wallet list, adapters pinned by commit; see fixtures/wallets/near-connect.json). The local sandbox test signer is a local sandbox adapter, not a wallet. It is offered only when this page is served by tools/src/console/serve.ts, signs with a sandbox key in a Node process on this machine, refuses other chains and signs only the owner calls this console offers on the served deployment. The manual handoff shows the exact near CLI command and tracks the hash you paste.
  • Which wallets are verified. The NEAR Connect path (wallet list, sandboxed adapter, signature request, cancel, hash import) is tested end to end in a local sandbox with the labelled SANDBOX TEST WALLET only. No real wallet provider has signed through this console yet: compatibility with the owner's actual wallet is an owner-assisted check, and nothing here claims it.
  • Wallet adapters' own storage. An adapter granted storage keeps its session data in this site's browser storage under its wallet id. That is the wallet's data, not a key held by this page's code.
  • The runner verifies. The handoff record (intent sha256, transaction hash, signer) is imported by the runner, which checks the chain, signer, key, receiver, every action and argument, the receipt tree and the end state. The console's own final-state display is a convenience, not that verification.
  • Never resubmitted. With the local test signer, a cancelled signature or a rejected transaction leaves nothing pending. A wallet's rejection or closed window stays pending until you forget it, because a wallet's error cannot prove that nothing was sent. A reload during a pending action resumes polling only.
